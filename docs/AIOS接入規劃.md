## 0. 目標與分工

目標：George 在 18 吋螢幕前 1.5–3 m 處用語音說「客廳燈關掉」「冷氣調 26 度」「現在濕度多少」，由 AIOS 的即時語音呼叫中控完成。

| 項目 | 由誰負責 |
|---|---|
| 設備清單、狀態、感測值、控制、回讀確認、權杖與稽核 | **中控（本 repo）** |
| 語音理解、名稱對應、確認卡、畫面呈現、與鏡頭在場偵測整合 | AIOS |

中控維持現有原則不變：
- 送出控制後回讀，結果分為 `confirmed / unconfirmed / failed`。
- 紅外線只做單向送出，不推測家電狀態。
- 不產生模擬讀值。

AIOS 只是另一個 API 呼叫者，不繞過這些規則。

## 1. 連線方式（決定）

```
AIOS 本機核心（Mac）──REST v1 + SSE（區網、Bearer 權杖）──► 中控 :8788
```

- **由 AIOS 本機核心呼叫中控，不經雲端**。
  - AIOS 的即時語音是 OpenAI Realtime。若用它的遠端 MCP 功能，會由 OpenAI 的伺服器連進來，等於要把家庭控制開放到公網，所以**不採用**。
  - 改由 AIOS 本機核心提供 `home_*` 函式工具，在本機呼叫中控 REST。
- **兩台機器可以不同**：AIOS 與中控可以在同一台 Mac，也可以在區網內不同機器。中控需綁定區網介面（README 已說明）。
- **MCP 伺服器延後**：作為第 3 階段選項，給 AIOS 的背景 Agent 使用（§5 P3）。

## 2. 需要補的介面

依優先度排列。P0 是 AIOS 接入前的必要條件。

### P0-1 權限範圍權杖（目前所有權杖都是完整管理權限）

讓 AIOS 拿到的權杖只能讀狀態和送允許的指令，不能改配置、匯出、管理權杖或上傳模型。

```json
POST /api/v1/access-tokens
{
  "name": "AIOS 即時語音",
  "scopes": ["devices:read", "telemetry:read", "commands:write", "events:read"],
  "device_allowlist": null,
  "command_allowlist": ["power", "brightness", "temperature", "color", "volume", "mute", "play", "pause", "stop"]
}
```

- `scopes` 缺省時沿用完整權限，以相容既有權杖。
- `device_allowlist` 可限制只能控制某些設備（null 表示全部）。
- 中控在每個需要驗證的路由檢查 scope，不足時回 403，並寫入事件。
- UI 的「系統接入」頁顯示每個權杖的 scope，並可撤銷。

### P0-2 每個指令的風險等級（給 AIOS 決定要不要語音確認）

在設備能力回傳中加上 `risk` 與 `confirmable`：

```json
"commands": [
  {"command": "power", "risk": "low", "confirmable": true},
  {"command": "temperature", "risk": "medium", "confirmable": true},
  {"infrared_key": "power", "risk": "medium", "confirmable": false}
]
```

| 等級 | 例子 | AIOS 的處理 |
|---|---|---|
| low | 燈開關／亮度、音量、暫停播放 | 直接執行，語音回報結果 |
| medium | 冷氣溫度／模式、除濕機、窗簾、紅外線按鍵 | 語音說「確認執行」才送出 |
| high | 洗乾衣啟動、會長時間耗電或有安全疑慮的設備（未來門鎖、瓦斯） | 語音確認，且只接受固定語句；也可以設為不開放語音 |

- **預設規則由中控提供**：依轉接器與指令判斷。紅外線一律 `confirmable: false`，因為無法回讀。
- **使用者可以逐台覆寫**：在設備詳情調整風險等級。
- **AIOS 不自行猜風險**。

### P0-3 名稱解析（語音說的是名字，不是 ID）

```
GET /api/v1/resolve?q=客廳燈&kind=device
→ [{"device_id": "...", "name": "客廳主燈", "room": "客廳", "aliases": ["客廳燈"], "score": 0.92}, ...]
```

- **比對方式**：依名稱、別名（含既有外部名稱對應）、房間做比對。
- **只做確定性比對**：完全相同、包含關係、注音／同音字表，不呼叫雲端 LLM。
- **回傳候選清單**：同分時一併回傳，由 AIOS 問「是客廳主燈還是客廳立燈？」。
- **房間清單**：`GET /api/v1/rooms` 回傳房間名稱與設備數，讓語音可以說「客廳的燈全部關掉」。

### P0-4 指令結果事件化

AIOS 要在語音中說「已確認關掉了」或「已送出，請確認」，需要即時拿到結果：

- **新增 SSE 事件**：`command.result`，內容為 `{command_id, device_id, status, message}`；狀態改變另送 `device.state`。
- **呼叫者識別**：事件帶 `caller`（權杖名稱），讓 AIOS 只處理自己送出的指令。
- **不延長回讀等待**：現有回讀等待時間不變，AIOS 自行處理逾時。

### P1-1 稽核

- **記錄內容**：每筆指令記錄權杖名稱、來源 IP、Idempotency-Key 與結果。
- **查詢介面**：「系統接入」頁可以篩選 AIOS 送出的指令。

### P1-2 群組指令

```
POST /api/v1/rooms/{room}/commands {"command": "power", "value": false, "kinds": ["light"]}
```

- **批次方式**：依現有單台指令逐台送出並各自回讀，回傳每台的結果，不宣稱整批成功。
- **風險取最高者**：整批的風險等級取其中最高的一台。

### P1-3 安靜時段與速率限制（每個權杖）

- **速率限制**：每分鐘最多 N 個控制指令，避免語音誤觸連發。
- **安靜時段**：可設定時段內只允許 low 風險。

### P2 情境（之後再做）

「我要睡了」這類多步驟情境，本 repo 的 README 已註明尚無通用情境引擎。先由 AIOS 把情境展開成多個單台指令，各自回讀；中控之後若要做情境引擎再另行規劃。

## 3. 不變的邊界

- 不新增公網存取；權杖只在區網使用。
- 金鑰仍只在中控；AIOS 只拿到範圍權杖，不拿任何廠商憑證。
- 不為了語音體驗把 `unconfirmed` 當成功、不產生推測狀態、不自動重送。
- 感測值缺值仍是 null，AIOS 會說「沒有讀值」而不是 0。

## 4. 測試

- **權杖範圍**：權限不足的權杖對每個寫入路由都回 403，且不會改到資料（pytest）。
- **風險等級**：各轉接器的預設風險表做 snapshot 測試；使用者覆寫後回傳覆寫值。
- **名稱解析**：用示例資料測完全相同、別名、同房間多台、無結果。
- **SSE**：`command.result` 帶 caller；重播（Last-Event-ID）仍正確。
- **相容性**：既有權杖（沒有 scope）行為不變。
